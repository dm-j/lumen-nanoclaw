# Post-turn topics agent, driven by real MCP-shim tools

**Discussed 2026-08-15, not started.** Lumen's working-memory bands (`Meta/working-memory/{now,soon,back-burner}.md`, see [Reconcile host-shim trunk templates](reconcile-host-shim-templates.md)'s addendum) are currently rewritten wholesale by three independent `focus-updater` dispatches per turn — each one freehand-regenerates its whole file from the incoming message. That's the first cut, not the intended end state:

- **Why:** three independent small-model calls each deciding "does this item belong in my band" from scratch, with no shared state, means dedup across bands is emergent (nobody's job) rather than guaranteed. A real `mcp__topic__set_topic`-style tool — add to Now, atomically remove from wherever else it was, code-enforced not model-inferred — would be strictly more reliable than freehand file regeneration, matching the general principle this session kept coming back to: LLM performance drops as responsibilities per call increase, so give each call one narrow, well-defined job with deterministic backing where possible instead of one model doing everything freehand.
- **Two dispatch points, not one.** `focus-updater` today only runs pre-turn (as part of `briefing-host`'s compile step, before Lumen even wakes) — it only ever sees the *incoming* message, never what Lumen actually decided or did. Topics/priorities can shift at either point (a message arrives that changes focus, or Lumen's own reply/actions during the turn change it) — the agreed design runs a topics-agent **both** before the turn (extending/replacing today's `focus-updater`) **and** after it, once Lumen's reply is known.
- **The "after" hook doesn't exist yet.** Nothing in the host pipeline currently runs after a projected-session turn completes and its `messages_out` row is written — this is the real new work, not a vault-side script edit like everything else built 2026-08-15. Natural candidates: `src/delivery.ts` (host polls `outbound.db`, already sees the completed reply) or the `processing_ack` sync in `src/host-sweep.ts` (already detects turn completion, but only on the ~60s sweep cadence — may be too coarse for "topics changed mid-conversation" responsiveness). Needs its own design pass, not a bolt-on.
- **MCP shims are a different subsystem than host-shims.** `briefing-host`/`focus-updater` are host-shim scripts (`host-shims/lumen-dmj/`, dispatched host-side via `execHostShim`). An MCP shim (`mcp-shims/`, `/add-mcp-shim` skill, registered per-group in `container_configs`'s `mcpShims`) is container-side tooling exposed as a real MCP tool — a bigger lift (container rebuild + restart, not just editing a vault file) than anything done in this session.
- **Decided:** the topics-agent's dispatch stays automatic/post-turn (not a live tool Lumen calls herself mid-turn) — consistent with the whole redesign's goal of keeping her own turn free of more responsibility, the same reasoning that moved working-memory maintenance out of Briefer's own turn and into a separate dispatch.
- **Not yet decided:** the exact shape of the "after" hook; whether `set_topic` needs sibling tools (`drop_topic`? `promote_topic`?) or one tool covers it; whether the pre-turn and post-turn topics-agent runs share one MCP-shim-backed implementation or stay separate.
