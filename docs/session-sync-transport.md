# Session Sync Transport — Investigation, Design, and Status

Why `container_configs.transport` exists, what was actually tried and ruled out before landing on it, and the design decisions for the parts not yet built — so this isn't re-investigated or re-decided from scratch later.

Related: [db.md §4](db.md#4-cross-mount-visibility) (the problem this replaces), [db-session.md](db-session.md) (today's `'file'` transport, still the default).

---

## 1. The problem

`inbound.db`/`outbound.db` are bind-mounted into the container so both host and container can open them. On macOS, this corrupts: `SqliteError: attempt to write a readonly database`, `database disk image is malformed`, recurring in production (`logs/nanoclaw.error.log`) across many sessions over weeks.

## 2. What was tried and ruled out (do not re-attempt without new information)

All four were verified empirically, not assumed — see chat history around 2026-08-13 for the full test transcripts if the reasoning here needs re-auditing.

| Approach | Result | Why |
|---|---|---|
| Docker named volumes (container-only storage) | Rejected before building | Host process (`session-manager.ts`) opens these files natively via `better-sqlite3` — a named volume has no host filesystem path at all on macOS (lives inside the Docker Desktop VM). Would require dockerizing the host itself. |
| Docker `--opt type=nfs` local volume, backed by macOS `nfsd` | Never actually worked | Docker Desktop 4.66's volume driver doesn't route `type=nfs` to a real NFS mount at all — every attempt went through Docker's own proprietary volume-backing layer (`backingFsBlockDev`/`metadata.db`, visible in the VM console log), confirmed by zero packets ever reaching `nfsd` on port 2049. True with `UseContainerdSnapshotter` both on and off. Architectural in this Docker Desktop version, not a config problem. |
| Consistency mount flags (`:cached`/`:delegated`) | Ruled out without testing | Legacy osxfs-only flags; no-ops under VirtioFS (Docker's default since 4.6+), which this install uses. |
| Apple Container (native macOS runtime, `container` CLI) | Fails the same class of problem | Stress-tested directly (bypassing Docker/NanoClaw entirely): a bidirectional read/write pattern matching real `inbound.db`/`outbound.db` traffic failed 3/3 runs (`unable to open database file`, `disk I/O error`). Apple Container uses its own VM-per-container VirtioFS-family mount — different implementation, same failure class. No corruption in these runs (`integrity_check` stayed `ok`), but the container process crashed every time. |

**What *is* proven safe**: a plain Docker-internal volume (`docker volume create`, no special driver options, never mounted on the host side at all) survived sustained hammering and a hard `SIGKILL` mid-write across 3 repeated trials — `integrity_check: ok` every time, zero data loss beyond the last committed row. The distinguishing factor across every test: **corruption only happens when the host filesystem-sharing layer (VirtioFS or NFS-over-Docker) is involved at all.** A file that never crosses that boundary is fine, on any runtime.

## 3. The design that follows from that

Don't fight the mount — remove it. Each side gets its own local, never-shared SQLite database; a sync channel reconciles them.

- **Host**: `inbound.db`/`outbound.db` stay exactly as they are today — host-native, host-only-opened, unchanged schema. Never mounted into the container again.
- **Container**: its own local SQLite on a plain Docker volume (the proven-safe kind above) — sole writer, sole reader, entirely internal to the container's own storage.
- **A WebSocket carries synced rows, not file access.** Each side commits locally first (durable immediately, no dependency on the peer being reachable), then pushes the new row to the other side, which commits its own copy and acks. This is what actually closes the durability gap a naive "container calls host, host is the only durable copy" design would have — see reasoning in chat history 2026-08-13, "SQLite has the virtue of durability" thread.
- **Hash-chain checksum**: `chain[n] = hash(chain[n-1] + canonicalize(payload[n]))`, one column, computed independently by whichever side wrote the row. Receiver verifies the chain as it applies each synced row; on mismatch, it sends back its last-known-good `(seq, chain)` and the sender replays from there using its own durable local copy. Implemented in `src/session-sync/protocol.ts` (host) and the container mirror, unit-tested.
- **Reconnect/resync**: "sync me everything since seq X," reusing the existing even/odd (host/container) seq-parity namespace — no new protocol concept.
- **Per-group opt-in**: `container_configs.transport` (`'file'` default, `'sync'` opt-in), materialized into `container.json`. Linux hosts have no VirtioFS layer and no observed corruption — the intent is `'file'` stays the permanent default there, `'sync'` becomes the macOS default only once proven out.

## 4. Transport-layer decisions, priced in ahead of need

Prompted by a live design question: does replacing a shared file with a WebSocket also enable running the container on a separate machine, and — further out — could other host-provided capabilities (channel adapters, filesystem access) become similarly location-independent? Answer: session-sync *does* stop caring where the container runs, but nothing else does yet (see §5). Three decisions were made cheap now specifically because they'd be expensive to retrofit if that direction is ever pursued — everything else stays deferred (§5) since nothing concrete motivates building it.

1. **`wss://` only — no plain `ws://` code path exists at all**, not "disabled by config." Same-box today (self-signed cert is fine), but there's no insecure mode to accidentally carry forward if a socket is ever reached off-box.
2. **Per-connection auth is a signed token** (HMAC over `sessionId + expiry` with a per-install secret), not a bearer string compared with `===`. Verified on WS upgrade.
3. **Message envelope carries a `channel` tag** (`{ channel: string, body: unknown }`), even though Phase 1 only ever sends `channel: 'session-sync'`. Costs one field now; means a hypothetical second channel later multiplexes over the same connection/auth code instead of forcing a protocol migration.
4. **Connection/auth code is factored separately from sync-message handling** — `session-sync/transport.ts` (generic: connect, authenticate, envelope routing) vs. `session-sync/server.ts` / container-side `client.ts` (sync-specific: chain verification, resync, DB writes). Registered as a handler, not hand-rolled per-socket logic.

## 5. Explicitly deferred — do not build without a concrete driver

Noted so the idea isn't lost, and so it isn't quietly reinvented under time pressure either:

- **Remote container execution.** Session-sync becoming location-independent doesn't make the *system* location-independent — `groups/<folder>` (skills, CLAUDE.md, working files), `.claude-shared`, `outbox/`/`inbox/` attachments are all still plain host bind mounts, unaddressed by this design. Spawning itself (`container-runner.ts`) shells out to a local `docker`/`container` binary — a remote target needs a Docker remote context (SSH/TLS) or different orchestration entirely.
- **Host-provided capabilities as remote services** (Telegram/other channel adapters, filesystem access, etc. reachable from a separate machine over the same kind of channel). A real, coherent future direction — genuinely enabled by §4's envelope tag — but there is currently exactly one channel (`session-sync`) and no second use case driving a build. Building service discovery, a capability registry, or a second channel now would be speculative flexibility with no proven need.

## 7. `session_sync_state` vs. `session_state`

`session_sync_state` (schema.ts) is host-internal bookkeeping for the sync transport itself (currently just the outbound chain checkpoint — see §6 Phase 1). `session_state` is container-owned application state (SDK session ID, etc.), synced or not depending on the Phase 2 scope decision above. Kept as two separate tables specifically so sync-internal bookkeeping never shares a keyspace with app state that Phase 2 might start syncing — a collision there would be silent and hard to trace back to this decision.

## 8. Reversible switchover plan (planned 2026-08-15, not built)

Written before the mount-flip + write-path rewrite (§6 Phase 2's last item) rather than after, so the rewrite is built *to* this plan instead of the plan being reverse-engineered from whatever the rewrite happened to make possible.

### 8.1 The invariant the rewrite must preserve

`'sync'` transport must never become the *only* durable copy of anything. Today, host-side `inbound.db`/`outbound.db` are always the complete record regardless of transport (§6 verified this directly: `writeSessionMessage` inserts unconditionally; `notifyInboundWrite` — and after the rewrite, the container's push — is additive on top; `makeSessionSyncHandler` writes into the exact same `outboundDbPath()` `delivery.ts` always reads). The rewrite must keep that true: the container's local DBs become an additional durable copy for the container's own use, not a replacement for the host's. This is what makes switching transport, in either direction, a config change plus a restart rather than a data migration — there is never a moment where a session's history exists in only one place with no fallback.

The one place this invariant is *not* automatically satisfied is a container's own unpushed writes at the exact moment it's killed — see 8.2.

### 8.2 Hard prerequisites (block any real cutover, not just nice-to-haves)

None of these are optional polish — shipping without them means a transport flip can silently lose data, not just degrade:

1. ~~**Reconnect loop**~~ — **done** (`container/agent-runner/src/session-sync/startup.ts`'s `maintainConnection`). On socket close, retries with backoff (1s/2s/5s/10s/30s, capped) using the freshest token the client has seen from `AUTH_CHANNEL` rather than re-reading the spawn-time credentials file — so a session outliving one token's TTL, or surviving a host restart, keeps syncing without a container respawn. The same `SyncClientHandle` (chain state, pending pushes) survives across reconnects; only the socket is replaced. 19 container-side tests pass, including a reconnect-timing test.
2. ~~**Drain-before-exit on graceful shutdown.**~~ — **done**. `SyncClientHandle.drain(timeoutMs)` (`container/agent-runner/src/session-sync/client.ts`) resolves once every in-flight push is acked, or after the timeout — it never rejects or hangs, it just reports how many pushes are still outstanding so the caller can log and exit anyway. `index.ts`'s `registerShutdownDrain` hooks this to `SIGTERM`/`SIGINT` (no-op when not on `'sync'` transport) with a 600ms bound. That bound has to fit inside the host's existing kill grace period — `container-runtime.ts`'s `stopContainer()` runs `docker stop -t 1` (1s total before SIGKILL) for every container today, sync-transport or not. 600ms leaves headroom but is untested against a real network round trip under load; **if drains start timing out in practice, the fix is a longer `docker stop` grace for sync-transport sessions specifically, not a longer in-container timeout** (SIGKILL doesn't care how long the container *wants* to wait). This still doesn't cover the ungraceful paths — `SIGKILL`, `process.exit(75)` — no signal exists to hook into for either; only the `--init`-forwarded `SIGTERM` path is coverable at all, which is the case a routine `docker stop`/`ncl groups restart` always takes.
3. ~~**`inbound.db` full-schema sync**~~ — **done** for the wire path (`delivered`/`destinations`/`session_routing`, §6 Phase 2), and **done end-to-end** as of the mount-flip + write-path rewrite (§6 Phase 2's last item) — `applyInboundRow` now dispatches all four kinds into the container's local `inbound.db` (`session-sync/apply-inbound.ts`), not just logging and dropping. `SyncMessageKind` gained three values (`'delivered' | 'destinations' | 'session_routing'`, mirrored both sides); `src/session-sync/inbound-push.ts` gained `notifyDeliveredWrite`/`notifyDestinationsWrite`/`notifySessionRoutingWrite`, all routed through the same `pushInboundRow` (already kind-generic) as `messages_in`. Wired at all three host write sites: `delivery.ts` (after `markDelivered`/`markDeliveryFailed`, which now return the row they wrote so the pushed payload matches exactly), `modules/agent-to-agent/write-destinations.ts` (after `replaceDestinations`), `session-manager.ts`'s `writeSessionRouting` (after `upsertSessionRouting`). All four inbound-direction kinds share one `inbound_seq`/`inbound_chain` per session, same as the four outbound-direction kinds already share `outbound_seq`/`outbound_chain`. What full-schema sync still doesn't cover: the on-connect backfill for a write that landed *before* the connection existed (§8.6.1/§8.6.2 close this for `destinations`/`session_routing`/`messages_in` specifically — `delivered` is the one table still exposed, flagged in §8.6.4) and reconnect-time replay for a write that lands *while disconnected* (next item, still open).

**Seq reservation fix (2026-08-15).** Multiplying the inbound-direction kinds to four surfaced a latent race in both `pushInboundRow` (`src/session-sync/server.ts`) and `push()` (`container/agent-runner/src/session-sync/client.ts`): both used to compute `seq = state.seq + 1` synchronously but only mutate `state.seq` inside the ack's `resolve()` callback, which fires after a full round trip. Two pushes for the same session fired in the same tick — e.g. `delivery.ts`'s undelivered-message loop calling `notifyDeliveredWrite` per message without awaiting between calls — would both compute the identical next seq; the second `pending.set(seq, ...)` silently overwrote the first, leaking a waiter that could never resolve or reject (and, post-§8.2.2, would make `drain()` always burn its full timeout on the leaked entry). Fixed by reserving the seq synchronously at call time, immediately after computing `chain`, before the async round trip — both sides now advance `state.{in,out}bound` before returning the pending promise, not inside it. Regression-tested in both `server.test.ts` and `client.test.ts` (fire two pushes unawaited, assert distinct seqs, assert both eventually resolve) — these tests fail against the pre-fix code.

4. **Reconnect-time backfill for writes made while disconnected** — **done**, for the one gap that was concrete (`delivered`, §8.6.4); chose option (a) over the general chain-replay resync, since it was the fourth instance of the same shape but still cheap and scoped, and nothing yet motivates the general mechanism. `delivered` (`src/db/schema.ts`) gained a `sync_acked INTEGER NOT NULL DEFAULT 0` column (lazily ALTERed onto existing sessions via `migrateDeliveredTable`) — the per-row watermark `messages_in`'s `status='pending'` filter already gave that table for free. `notifyDeliveredWrite` (`src/session-sync/inbound-push.ts`) now takes an optional `inboundDbPath`; once the container acks the push, it calls `markDeliveredSynced` (`src/db/session-db.ts`) to set the flag. `backfillPendingDelivered` (`src/session-manager.ts`), mirroring `backfillPendingInbound`, re-pushes every `sync_acked = 0` row and is wired into the same `onConnect` hook as the other three backfills (`src/index.ts`). Idempotent on the container side (`INSERT OR IGNORE` in `apply-inbound.ts` — a `delivered` row's content never changes once written, so a resend is a no-op, not a stale overwrite like `messages_in`'s staged→pending case). The general chain-replay resync (option b) is still not built — remains the fallback if a fifth instance of this bug class ever turns up somewhere `sync_acked`'s per-row-column trick doesn't fit.

### 8.3 Mechanism (already exists, nothing new to build)

Switching a group's transport is already just:

```
ncl groups config update --id <group-id> --transport sync    # or: file
ncl groups restart --id <group-id> --message "transport changed"
```

`--message` forces the `on_wake` respawn path (`container-restart.ts`) so the switch takes effect immediately rather than waiting for the next natural wake — and, per 8.2, only after the old container has actually drained and exited (`killContainer`'s existing `onExit` callback already guarantees the old process is gone before the new one spawns).

### 8.4 Staged rollout

1. **Canary group**: one low-stakes agent group (an admin's own personal/test group, not anything a real user depends on) — never the owner agent group, never anything wired to a channel with real traffic, for the first cutover.
2. **Observation window**: a few days of normal use, not a synthetic load test alone — the corruption this whole effort exists to fix only ever showed up under real, sustained traffic patterns (§1).
3. **Per-cutover verification checklist** (grep `logs/nanoclaw.log`/`nanoclaw.error.log`):
   - `Session-sync server listening` at host boot (already always true) and `connected to host session-sync server` from the specific container after its next spawn.
   - No `session-sync: chain resync required` / `resync_point` lines for that session — any occurrence means the two sides' chains diverged, which after the rewrite should never happen in normal operation and is itself an abort signal (8.5).
   - No new `DB_RETRY_EXHAUSTED` lines for that session's ID — the existing `sqlite-corrupt-count-host` shim (`docs/host-shims.md`) already tracks this metric and can be pointed at the canary group directly.
   - A real round-trip: send the canary group a message, confirm the reply, confirm `ncl sessions get` and `ncl tasks list` (if it has scheduled tasks) still behave normally.
4. **Widen gradually**: one more real (but non-critical) group, then the rest, each getting its own few-day observation window — never a single flip-the-default-for-everyone commit.

### 8.5 Rollback

Because of 8.1, rollback is symmetric to cutover and just as cheap:

```
ncl groups config update --id <group-id> --transport file
ncl groups restart --id <group-id> --message "transport changed"
```

The next container spawns back under `'file'` transport, bind-mounts the host's `inbound.db`/`outbound.db` as always, and — per 8.1 — those files were never anything other than the complete record the whole time. No data migration, no "reconcile the two copies" step, because there was only ever one copy that mattered on the host side.

**Abort criteria** — roll back immediately, don't investigate-in-place on live traffic, if any of these show up for a cutover group:
- Any `resync_point`/chain-mismatch log line (8.4's checklist item — the rewrite should make this impossible in normal operation, so seeing one means a real bug, not noise).
- A user-reported message that never arrived or a reply that never sent.
- The container crash-looping or repeatedly failing to reconnect.

### 8.6 First real canary attempt (2026-08-16) — rolled back, findings below

The owner agent group (`lumen-dmj`, against §8.4's own explicit "never the owner group" guidance — a deliberate, informed exception, not an oversight) was flipped to `'sync'` transport for a real test. Rolled back after ~40 minutes once a structural gap was confirmed; Lumen was degraded (not receiving/replying to messages) for that window. Four real bugs were found and fixed along the way — all worth keeping regardless of when `'sync'` transport is retried:

1. **TLS cert SAN didn't cover `host.docker.internal`** (`src/session-sync/cert.ts`) — the container connects through that hostname, not `localhost`/`127.0.0.1`; every connection failed hostname verification. Fixed by adding it to the SAN list.
2. **The actual root cause, SAN was a red herring**: under Bun, `ws`'s `WebSocket` constructor silently drops top-level `ca`/`rejectUnauthorized` options — confirmed empirically (a matching-SAN, correctly-pinned connection still failed the handshake; `rejectUnauthorized: false` still failed). Wrapping them in an `https.Agent` and passing that as `agent` is what actually works under Bun (`container/agent-runner/src/session-sync/transport.ts`). Also added `checkServerIdentity: () => undefined` on the agent — CA pinning alone is the real security boundary (only a cert backed by the host's private key can complete the handshake); hostname verification can't generalize across deployment environments (Docker Desktop vs. Linux gateway IP vs. a future remote agent) and was dropped as unnecessary belt-and-suspenders.
3. **`applyInboundRow` had no try/catch in `client.ts`'s message handler.** A thrown exception there gets silently absorbed by `ws`'s internal frame handling (confirmed against a live container — no crash, no error log) — the ack never sends, the host's `pushInboundRow` promise hangs forever unresolved, and the row never lands locally. No timeout exists on either side's pending-push map, so this was a silent, permanent hang, not a visible failure. Now caught and logged loudly; the underlying "why did it throw" question wasn't fully chased once the bigger structural gap below made further live debugging moot.
4. **`releaseStagedMessage` (`src/session-manager.ts`) never pushed its `staged → pending` status flip.** `writeSessionMessage`'s `stage: true` option exists specifically for an already-warm container racing the host's own synth step — exactly the state Lumen was in for most of this test. The initial insert (status `'staged'`) gets pushed, but the flip to `'pending'` didn't, so the container's local copy of the row was permanently stuck at `'staged'` — invisible to `getPendingMessages()`'s `WHERE status = 'pending'` filter for the life of that container. Fixed: `releaseStagedMessage` now pushes the released row too.

**The structural gap that forced rollback**: `write-destinations.ts` and `writeSessionRouting` (`src/session-manager.ts`) write their setup snapshot **at spawn time, before the container has connected** — confirmed via the exact sequence: destinations/routing writes fire, `notifyDestinationsWrite`/`notifySessionRoutingWrite` no-op (`if (!ws) return` — no connection exists yet at that point), *then* the container spawns and connects a few seconds later. Under `'sync'` transport this means **the container's local `destinations` table is permanently empty** — there's no "container connects → host sends the current snapshot" handshake, only a stream of future writes. Symptom: the agent processed a message correctly and tried to reply, but `<message to="...">` name resolution failed (`Unknown destination`, block dropped) — the reply was silently never sent. This is exactly the Phase 3+ backfill/resync gap already called out throughout this doc (§8.2.1, §6), just landing on the one piece of data every session structurally depends on at spawn.

**What a real cutover needs that doesn't exist yet**: some form of "on connect, push the current destinations + session_routing snapshot" step — not necessarily full Phase 3+ resync/backfill for every table, but at minimum this one, since it's unconditionally required for every session to function at all, not an edge case. Until that exists, `'sync'` transport is not safe to use for any group with real traffic, canary or otherwise.

### 8.6.1 On-connect backfill (2026-08-17) — built

Closed the gap above. `createSyncServer` (`src/session-sync/transport.ts`) now takes an optional `onConnect(sessionId)` callback, fired right after a WS handshake completes (`connections.set` in the `handleUpgrade` block) — i.e. exactly the moment `notifyDestinationsWrite`/`notifySessionRoutingWrite` stop being no-ops for that session. Wired in `src/index.ts`'s `createSyncServer` call: on connect, it re-runs `writeDestinations` (agent-to-agent module, if installed) and `writeSessionRouting` (`src/session-manager.ts`) for that session — the same two functions spawn-time already calls. Both are idempotent (`replaceDestinations`/`upsertSessionRouting` are full-replace/upsert), so re-running them on every (re)connect, not just the first, is correct and cheap — a reconnect after a network blip gets a fresh snapshot for free with no separate resync-path needed for these two tables specifically. Regression test: `src/session-sync/transport.test.ts`'s `createSyncServer onConnect` suite (asserts the callback fires with the connecting session's id).

This does not touch the broader Phase 3+ resync/backfill gap (§8.2.1) — `delivered` rows written while disconnected are still simply lost, no chain-replay exists. But the one gap that made `'sync'` transport non-functional for *every* session (not just an edge case) is now closed. Before the next canary attempt: re-verify no other spawn-time-only write exists with the same "written before connect, never backfilled" shape.

### 8.6.2 Second canary attempt (2026-08-16) — the triggering message itself raced the same gap

Re-flipped Lumen to `'sync'` transport with §8.6.1's fix live. First real message: container spawned, connected (`[session-sync] connected to host session-sync server` logged), then hung forever with no further output — no poll-loop line, no error, no crash. Same silent-hang shape as §8.6 item 3, but that fix (try/catch around `applyInboundRow`) doesn't apply here because nothing throws — the container is just correctly, quietly waiting for a `messages_in` row that will never arrive.

Root cause: `routeInbound()` writes the triggering `messages_in` row and *then* spawns the container. Connecting takes a real, multi-second TLS round trip (cert load, handshake, auth token verify) — so by the time the container is connected, the message that woke it was already written with no live `ws` to push through (`notifyInboundKindWrite`'s `if (!ws) return`). This is the exact same "written before connect" race as §8.6's finding, just landing on `messages_in` instead of `destinations`/`session_routing` — and worse, because it's not an edge case at all: routing-then-spawn is the *normal* wake path for every single message under `'sync'` transport, so every first message to a cold container would race this.

Fixed the same way: `backfillPendingInbound(agentGroupId, sessionId)` (`src/session-manager.ts`) reads every `status = 'pending'` row from the host's `messages_in` and re-pushes it via `notifyInboundWrite` on every connect, called from the same `onConnect` hook right after the destinations/routing backfill. Idempotent on the container side (`INSERT OR IGNORE`), so a reconnect re-sending an already-applied row is harmless. Verified live: killed the stuck container, host rebuilt+restarted, a fresh container spawned, connected, received the backfilled message, and replied in ~6 seconds (`docker logs` showed `poll-loop] Processing 1 message(s)` immediately after the connect line, then the reply). No `resync_point`/error-log entries.

**Status**: with both backfills in place, `'sync'` transport now completes a full real round trip (message in → agent reply → Telegram delivery) on the owner group with no observed gap. Recommend running it longer under real traffic (a day+) before calling it broadly safe, since Phase 3+ resync (disconnected-window writes, `delivered` table) is still genuinely unbuilt — this only closes the "every session is broken from message one" class of bug, not full durability under a mid-conversation disconnect.

### 8.6.3 Third canary attempt (2026-08-16) — staged→pending flip silently dropped

With both backfills live, the first message got a reply. A second message sent moments later, while the container was already warm and connected, got no reply — no error, no hang visible in `docker logs` (which showed nothing past the first reply). This is the "already-warm container" wake path: `writeSessionMessage`'s `stage: true` option inserts the row as `status='staged'`, and `releaseStagedMessage` later flips it to `'pending'` and pushes again — same `id`, same `seq`, only `status` differs.

Root cause: `applyMessageIn` (`container/agent-runner/src/session-sync/apply-inbound.ts`) used `INSERT OR IGNORE` keyed on `id`. The first push (staged) inserted the row; the second push (pending) was silently ignored because a row with that `id` already existed — the row was permanently stuck at `'staged'` in the container's local `messages_in`, invisible to `getPendingMessages()`'s `status = 'pending'` filter, for the life of that container. Confirmed by reading the container's local `.sync-local/inbound.db` directly: the message was present with `status: "staged"`.

This is a different bug from §8.6 item 4 (`releaseStagedMessage` not pushing at all, already fixed) — that fix made the push happen; this one is about what the container does once it receives that second push. `INSERT OR IGNORE` is correct for genuine retry-idempotency (a resend of an identical row must not throw or duplicate) but wrong for a legitimate status-changing update to an existing row.

Fixed: `INSERT ... ON CONFLICT(id) DO UPDATE SET status = excluded.status` instead of `INSERT OR IGNORE`. Container-side only (`container/agent-runner/src/`, no host rebuild needed) — a container restart picks it up. Verified live: restarted Lumen's container, the previously-stuck staged message and the restart's own on-wake message both processed and replied on the next spawn.

### 8.6.4 Audit for a fourth instance of the same bug class (2026-08-16) — none found, one flagged

After three rounds of "host write raced a missing connection" bugs on three different tables, audited every `writeSessionMessage`/`writeDestinations`/`writeSessionRouting`/`notifyDeliveredWrite` call site in the codebase for a fourth. Every non-destinations/routing inbound write (agent-to-agent routing, approvals, self-mod, host-shim, attachment-caption, container-restart, `create_agent`'s `notifyAgent`) funnels through `writeSessionMessage` → `messages_in`, and `backfillPendingInbound` (§8.6.2) is generic per-table, not per-call-site — so all of these are already covered, confirmed by the second canary message (a different code path than the first) working correctly.

One table shares the underlying fragility in a different shape: `delivered` (`notifyDeliveredWrite`, from `delivery.ts` after a channel adapter confirms send). It can't race the *spawn* — the container must already be connected to have produced the outbound message being marked delivered — but it can race a *disconnect*: if the container is killed (absolute-ceiling, or a short-lived task-triggered container) between sending its reply and the delivery confirmation landing, the push silently no-ops with no backfill to catch it on the next connect. This isn't a new bug class, just the already-documented Phase 3+ resync gap (§8.2.1) landing on the table most likely to actually hit it, given how often task containers are short-lived. Not fixed here — flagged as the next thing to check if something looks desynced after this round of fixes.

### 8.9 General chain-replay resync (2026-08-16) — built ahead of a concrete driver

§8.2 item 4's option (b) — built on request, not because a fifth bug instance surfaced (§8.6.4's audit found none; every current table already had a working backfill path). Scoped to the one direction that actually needed it: host-to-container ("inbound"), the only direction where a push can be sent, the socket can drop before the ack lands, and nothing else notices — the outbound direction has no equivalent gap because the container is sole writer of its own outbound stream and never queues a push it can't complete before dying (drain, §8.2 item 2).

Mechanism: `session_sync_log` (new table in `outbound.db`, `src/db/schema.ts`) — the host, chain-authority for the inbound direction, durably logs every `pushInboundRow` call (`seq`, `kind`, `chain`, raw JSON `payload`) before sending, alongside the existing in-memory `pendingInboundBySession` waiter map. Two replay triggers, same underlying `replayInboundLog` (`src/session-sync/server.ts`):

1. **Chain-mismatch `resync_point` from the container** — previously just rejected the pending push with an error; now replays everything logged after the container's reported point over the same socket.
2. **Reconnect** — `createSyncServer`'s `onConnect` callback now also receives the fresh `ws` (signature change, `src/session-sync/transport.ts`); `replayPendingInbound` resends every push still in `pendingInboundBySession` (i.e., sent before the disconnect, never acked) over the new socket, computing the resend floor as the lowest still-pending seq minus one.

No client-side (container) change needed — a replayed row looks identical to a first-time push, so `client.ts`'s existing chain-verify-then-apply-then-ack path handles it with no new logic. `session_sync_log` is unbounded (no trim) — an accepted first-cut tradeoff, noted in the schema comment; revisit if a session's log ever becomes large enough to matter (unlikely: only host-initiated pushes are logged, which are `messages_in`/`delivered`/`destinations`/`session_routing` writes, not every chat turn).

Tests: `src/session-sync/server.test.ts` (`replayPendingInbound resends unacked pushes...`, `...is a no-op when nothing is pending`, and the existing chain-mismatch test rewritten to assert replay instead of rejection); `src/session-sync/transport.test.ts`'s `onConnect` test updated for the new two-arg callback signature.

### 8.10 `cli/host-shim.ts` / `cli/ncl.ts` under 'sync' transport (2026-08-16) — closed, and it was a corruption risk, not just a gap

§6 Phase 2 flagged this as merely "explicitly out of scope." It's worse than that on inspection: both CLIs hardcode `/workspace/{inbound,outbound}.db` and open raw `bun:sqlite` connections directly against them — the host-mounted files. Under `'sync'` transport the host is *also* writing into that same mounted `outbound.db` (`applyOutboundRow` in `server.ts`, replicating the container's sync pushes). Running `ncl` or a host-shim from inside a `'sync'`-transport container therefore put two independent writers on the same VirtioFS-mounted file — the exact concurrent-writer pattern `'sync'` transport exists to eliminate (§1). Not inert: a live regression path back to the original corruption bug, scoped to whenever an agent actually invokes `ncl`/a host-shim.

Fixed via `container/agent-runner/src/cli/sync-outbound-push.ts`, shared by both CLIs. Under `transport: 'sync'` (read from `/workspace/agent/container.json`, no import needed — same file `config.ts` parses for the main runner):

- **Write path**: `writeAndPushSystemMessage`/`pushCompletedAck` insert into the container's own local `.sync-local/outbound.db` (never the host-mounted file) and push the row to the host over a short-lived sync connection, reusing the same chain-hash protocol (`protocol.ts`) and `session_sync_state` row that the persistent agent-runner client (`client.ts`) uses for its own outbound pushes.
- **Read path** (the response): already worked correctly with no changes needed — a host-pushed `cli_response`/`host_shim_response` lands in `.sync-local/inbound.db` via the persistent client's existing `applyInboundRow` path, so `pollResponse` just needed to read from there (`localInboundPath()`) instead of the host-mounted file under `'sync'` transport.
- **Cross-process coordination**: the persistent agent-runner client and a short-lived CLI invocation can both try to advance the same outbound chain sequence at once. Coordinated with a simple `O_CREAT|O_EXCL` lock file in `.sync-local/` (breaks a stale lock after 15s, e.g. from a crashed process) around the read-chain / connect / push / persist sequence. Safe because `.sync-local/` is only ever touched from inside the container (never the host), so there's no VirtioFS coherency concern for the lock file either — same property that makes `.sync-local/` itself safe.
- **`processing_ack` still gets pushed, not just written locally** — `host-sweep.ts` reads `processing_ack` on the host's own `outbound.db` to sync `messages_in` status and detect stale claims; a purely-local ack would leave the host thinking a `cli_request`'s response message was never handled, risking a spurious stuck-container restart.
- **Deliberately not importing `connectSyncClient` from `session-sync/transport.js`**, despite it doing exactly this connection handshake already — `bun:test`'s `mock.module()` patches are process-global (documented in `transport.test.ts`'s own header), `session-sync/startup.test.ts` mocks that exact module, and a snapshot-at-load-time capture of the export didn't reliably avoid the leak (bun appears to run different test files' `it()` bodies concurrently within one process, so there's no reliable "before any mock.module() call ran" point). The connect handshake (~30 lines, same Bun/`ws`-agent TLS workaround `transport.ts` documents) is reimplemented locally in `sync-outbound-push.ts` instead, fully decoupling this module's production behavior from that file's test-time mocking.

Tests: `container/agent-runner/src/cli/sync-outbound-push.test.ts` (5 tests — transport detection, write+push, chain-seq ordering across two calls, ack push, and a real timeout-rejection case against a closed connection), using a real self-signed-cert WSS test server (same pattern as `session-sync/transport.test.ts`). Full container suite (219 tests) and typecheck verified clean, including 3 repeated full-suite runs to confirm no flake from the mock-isolation issue above.
